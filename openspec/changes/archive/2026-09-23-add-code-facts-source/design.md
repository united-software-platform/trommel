## Context

Мотивация — в `proposal.md`, раздел «Why». Здесь только то, что задаёт границы решения.

Устройство прогона Trommel на сегодня:

- `rules.Implementation` объявляет `Subject()` — предмет, без которого правило не проверяется.
  Предметов три: дерево файлов, текст сообщения коммита, путь обращения. Все три передаёт
  вызывающая сторона ключами командной строки.
- `harness.Run` отвечает на три вопроса подряд: намерение выражено (`intent.Load`,
  `file.Select`), намерение исполнимо (`catalog.Load`, `registry.Dangling`, `checkSubjects`),
  намерение исполнено (`report`). Отрицательный ответ на любой из первых двух прекращает
  работу до обращения к содержимому проекта.
- Проверяемый проект приходит как `fs.FS` (`os.DirFS`) и в образе монтируется только на чтение;
  цель `trommel-image-verify` проверяет, что запись в него отклоняется.
- Образ выполнения — `alpine:3`, в нём один статический бинарник без CGO.

Что даёт tldr-code — зафиксировано по его `README.md`, `docs/INSTALL.md`, `docs/ARCHITECTURE.md`
и `docs/MCP.md` (версия релиза `v0.4.0`, 11 мая 2026):

| Уровень | Что строит | Команды | Форма вызова |
|---------|-----------|---------|--------------|
| L1 AST | Структура файла: функции, классы, импорты | `tree`, `structure` | проектная |
| L1 AST | То же по одному файлу | `extract`, `imports`, `importers` | точечная |
| L2 Call Graph | Вызовы между файлами и модулями | `calls`, `dead` | проектная |
| L2 Call Graph | Влияние изменения функции | `impact`, `hubs`, `whatbreaks` | точечная |
| L3 CFG | Поток управления внутри функции | `reaching-defs`, `available` | точечная |
| L4 DFG | Определения и использования переменных | `dead-stores` | точечная |
| L5 PDG | Зависимости управления и данных, срезы | `slice`, `chop`, `taint` | точечная |

Вне уровней, но по предмету примыкает к L1: `deps` — граф импортов, циклы и метрики связности,
форма вызова проектная.

Принадлежность команд уровням взята из справки самого анализатора: она расходится
с `docs/ARCHITECTURE.md` репозитория анализатора в отнесении команд потока данных.

Сверх уровней: безопасность (`secure`, `vuln`, `api-check`, `resources`), метрики качества
(`complexity`, `cognitive`, `halstead`, `loc`, `churn`, `debt`, `health`, `hotspots`, `clones`,
`cohesion`, `coupling`), архитектура (`patterns`, `inheritance`, `surface`), контракты
(`contracts`, `specs`, `invariants`, `verify`, `interface`), поиск (`search`, `context`,
`definition`, `explain`; `semantic`, `similar`, `embed` — только в сборке с `--features
semantic`, тянущей модель около 110 МБ).

Формы вывода: `json` (умолчание), `text`, `compact`, `sarif`, `dot`. Языков — 18, включая Go.
Есть режим демона с LRU-кешем в памяти по ключу `hash(tool_name + arguments + file_mtimes)`
(`daemon start`, `warm`, `daemon stop`) и MCP-сервер `tldr-mcp` на stdio с 24 инструментами.
Лицензия — AGPL-3.0.

Проверено прогоном выпуска `0.4.0` по дереву Trommel (задача 1.2); подробности —
в [документе анализатора](../../../docs/tldr-code.md):

- **Musl-сборок нет.** В активах `v0.4.0` только `gnu` (`tldr-cli-x86_64-unknown-linux-gnu.tar.xz`,
  `tldr-cli-aarch64-unknown-linux-gnu.tar.xz`), и ни один выпуск musl не давал, хотя
  `docs/INSTALL.md` анализатора их обещает. Архив содержит три исполняемых файла: `tldr`,
  `tldr-daemon`, `tldr-mcp`.
- **Коды возврата различимы:** `0` — выполнено, `1` — ошибка выполнения, `2` — ошибка вызова.
  Но код `0` не означает полученных фактов: каталог без поддержанных файлов даёт `0`,
  пустой перечень и `language: null`.
- **Вывод усекается по умолчанию.** `calls` ограничивает число рёбер ключом `--max-items`
  (умолчание `200`) и сообщает `truncated`, `total_edges`, `shown_edges`. Значение `0`
  ограничение не снимает, а даёт пустой вывод.
- **Язык один на прогон.** Поле `language` единственное; прогон по дереву Trommel дал
  `language: "go"` и ровно 27 файлов `.go`. Файлы других языков в вывод не попали
  и в предупреждениях названы не были.
- **Собственного ключа исключения каталогов нет** — открытый вопрос закрыт. Есть только путь
  в аргументе и `--respect-ignore` у `calls`, учитывающий `.gitignore` и `.tldrignore`
  проверяемого проекта.
- **Разбор ничего не пишет:** прогон по дереву Trommel не изменил ни одного файла проекта
  и не оставил данных в домашнем каталоге.

## Goals / Non-Goals

**Goals:**

- Фаза подготовки принадлежит Trommel: состав среза, версия инструмента и исход подготовки
  решаются им, а не окружением, в котором его запустили.
- Внешняя модель данных анализатора не проникает в правила: правило видит фактовую модель
  Trommel.
- Подготовка укладывается в действующий порядок `harness.Run` — до исполнения правил,
  после проверки исполнимости намерения.
- Прогон остаётся самодостаточным: всё нужное лежит в образе, сеть при прогоне не нужна.

**Non-Goals:**

- Реализации правил `CLAR`, `DDD`, `CQRS` — отдельное изменение. Здесь срез собирается,
  но ни одно правило его ещё не читает, кроме образцовой реализации для самопроверки.
- Правила на фактах: срез собирается, но ни одно правило нормы его ещё не читает.
- Команды tldr за пределами уровней `L1`..`L5`: метрики, безопасность, контракты, поиск.
  Они зафиксированы в документе возможностей, но в срез не входят.
- Семантический поиск и любые возможности, требующие загрузки модели.
- MCP-сервер как канал агента: отдельный вопрос, к прогону Trommel отношения не имеющий.

## Decisions

### Канал управления — подпроцесс с разбором `--format json`

Trommel запускает `tldr <команда> <путь> --format json`, читает поток вывода и разбирает его.
Так фаза подготовки остаётся внутри прогона: отказ анализатора становится отказом прогона
в том же месте, где Trommel уже отказывает при неисполнимом контракте.

Рассмотренные варианты:

- **Файл фактов, собранный отдельным шагом.** Trommel перестаёт владеть составом среза: файл
  мог быть собран другой версией инструмента, на другом дереве и с другим составом уровней.
  Воспроизводимость вердикта пришлось бы доказывать содержимым файла, а не прогоном.
- **MCP-сервер `tldr-mcp`.** Канал агента, а не харнеса: stdio-протокол JSON-RPC рассчитан
  на диалог, а не на пакетный сбор, и добавляет в прогон долгоживущий процесс.

### Срез снимает все уровни, область ограничивает карта проекта

Стоимость съёма ограничивается не составом уровней, а областью: прогон принимает карту
проекта — что сканируем и что не сканируем, — и подготовка не выходит за её пределы
ни обращением к анализатору, ни содержанием среза.

Уровни делятся по способу съёма:

| Уровни | Команды | Обращений к анализатору |
|--------|---------|-------------------------|
| `L1`, `L2`, `deps` | `structure`, `calls`, `dead`, `deps` | по одному на сканируемый путь |
| `L3`, `L4`, `L5` | `reaching-defs`, `available`, `dead-stores`, `slice` | по четыре на функцию |

Перечень функций берётся с `L1`, поэтому уровень функций без уровня структуры неисполним —
это ошибка контракта, а не неудача прогона.

Замеры на выпуске `0.4.0` (задача 1.2): точечные команды стоят **0,03 с и 5,6 КБ на функцию**.
`auditch-search` — 131 функция, 56 файлов PHP — снимается целиком за **4 секунды и 0,7 МБ**.
`lenobl` — 36 859 файлов PHP — только на `structure` тратит **181 секунду и 75 МБ**, а полный
съём его функций занял бы около **полутора часов**. Разница между четырьмя секундами и полутора
часами — это и есть карта: она отделяет то, о чём проект спрашивает, от того, что просто лежит
рядом.

Проверено съёмом (задача 8.8): полный состав уровней с `auditch-search` — **3,9 секунды**,
56 модулей, 97 вызовов, 131 функция с фактами `L3`..`L5`, 176 КБ в машинной форме. Граница
среза назвала четыре файла: скрытый `.settings.php`, файл JavaScript и два файла Python —
анализатор определяет один язык на прогон, и всё, что вне этого языка, остаётся без фактов.
Тот же съём с картой `--scan lib` — 53 модуля и 126 функций, граница пуста: файлы вне карты
не являются непросмотренными, они просто вне области.

Рассмотренные варианты:

- **Ограничить срез проектными командами, точечные уровни не снимать.** Дёшево и предсказуемо,
  но правила потока данных остаются без фактов навсегда: `L3`..`L5` описывают ровно то, ради
  чего внешний анализатор и берут.
- **Снимать все уровни по всему проекту без карты.** На проекте вроде `lenobl` прогон
  превращается в полуторачасовой, то есть перестаёт быть прогоном.

`taint` и `chop` в съём не входят: `chop` требует двух строк, для которых нет осмысленного
умолчания, а у `taint` на доступных корпусах не удалось получить непустые `sources`, `sinks`
и `flows` — форма их элементов не проверена, и разбор был бы догадкой. Оба названы в документе
анализатора как неснимаемые.

### Поставка — готовый бинарник релиза, база образа выполнения меняется на glibc

В образ кладётся бинарник из активов релиза с закреплённой версией и проверкой контрольной
суммы; тулчейна Rust в сборке нет.

Поскольку musl-сборок релиз не даёт, база выполнения переводится с `alpine:3` на минимальный
образ с glibc. Стадия сборки Go, статическая компоновка `trommel`, непривилегированный
пользователь [DOCK-012] и владение рабочим каталогом [DOCK-013] сохраняются без изменений.

Рассмотренные варианты:

- **`gcompat` поверх Alpine.** Слой совместимости покрывает не всякий вызов glibc; отказ
  проявился бы на конкретном проекте и конкретной команде анализатора — то есть в вердикте,
  а не при сборке образа.
- **Сборка tldr из исходников под musl.** Возвращает в сборку тулчейн Rust и делает образ
  сборки тяжелее на порядок; выбор пользователя — готовый бинарник.
- **Отдельный контейнер-сосед.** Требует канала между контейнерами и общего доступа к дереву
  проекта — сложность, не оправданная одним вызовом на прогон.

### Внутренняя модель фактов отделена от вывода анализатора

Вывод tldr разбирается в собственные структуры Trommel: правило получает факты в терминах
нормы (модуль, слой, зависимость, вызов), а не поля JSON конкретного инструмента. Это прямое
применение [DDD-025](../../../rules/ddd.md#anti-corruption-layer-ddd-025026) и
[DDD-026](../../../rules/ddd.md#anti-corruption-layer-ddd-025026): внешняя модель
не проникает в домен.

Цена решения — отображение, которое придётся вести при смене формата вывода. Выигрыш:
версия 0.x меняет форму вывода без предупреждения, и при прямом чтении JSON правилами каждая
такая смена ломала бы все правила сразу, а не один разбор.

### Предмет проверки и место фазы в прогоне

Добавляется `Subject` «факты о коде» и поле среза в `rules.Context`. Подготовка встраивается
в `harness.Run` между проверкой исполнимости намерения и исполнением правил: состав уже
известен, поэтому анализатор запускается только когда в составе есть правило, которое требует
фактов, и только по объявленным контрактом уровням.

`checkSubjects` расширяется: для предметов, передаваемых вызывающей стороной, он остаётся
проверкой переданного, для фактов о коде — проверкой состоявшейся подготовки.

### Кеш и демон не используются

`daemon start`, `warm` и любые формы переиспользования ранее собранных данных в прогоне
не применяются: ключ кеша анализатора строится по времени изменения файлов, а вердикт обязан
зависеть только от содержимого. Каталог временных данных анализатора уводится за пределы
проверяемого проекта — проект остаётся доступным только для чтения.

Цена — время прогона: каждый прогон разбирает дерево заново. Для проектов, где это окажется
значимым, ускорение решается сужением области прогона, а не кешем.

### Карта применяется и до анализатора, и после него

Сканируемые пути карты передаются анализатору аргументом команды: обход дерева стоит ровно
столько, сколько в карте названо. Пути ответа приводятся к корню проекта, поэтому срез
не зависит от того, за сколько обращений он собран.

Исключения карты применяются после разбора, на стороне Trommel: собственного ключа исключения
у анализатора нет, и вердикт не должен зависеть от того, появится ли он в следующей версии.

### Версия анализатора закрепляется и проверяется

Версия задаётся аргументом сборки образа и проверяется в начале подготовки вызовом
`tldr --version`. Версия вне поддерживаемого сборкой диапазона даёт отказ в запуске: срез
неизвестного состава хуже отсутствия среза. Версия попадает в вердикт вместе с версией Trommel
и отпечатком каталога правил.

## Risks / Trade-offs

- **Лицензия AGPL-3.0 у анализатора при MIT у Trommel** → Вызов отдельным процессом
  компоновкой не является, и лицензия Trommel не меняется. Но образ распространяет оба
  бинарника: до публикации образа условия AGPL-3.0 на распространение проверяются отдельно,
  а в документации образа указывается происхождение и лицензия анализатора.
- **Смена базы образа выполнения** → Образ растёт, и проверки образа (`trommel-image-verify`)
  переписываются под новую базу. Вердикт `docs`-контракта при этом не меняется: правила кода
  остаются в состоянии `--`, и расхождение сводки покрытия было бы признаком ошибки.
- **Версия анализатора 0.x: состав команд и форма вывода нестабильны** → Версия закреплена,
  разбор отвергает неопознанную форму вывода отказом прогона, а не догадкой. Обновление версии
  становится отдельной задачей с прогоном самопроверки.
- **Скачивание бинарника при сборке образа требует сети** → Загрузка закреплена версией
  и контрольной суммой; собранный образ сети уже не требует. Сборка в закрытом контуре
  выполняется с заранее выложенного зеркала активов.
- **Уровни `L4` и `L5` дороги на большом дереве** → Состав уровней объявляет контракт;
  проект, которому нужна только структура и граф вызовов, не платит за поток данных.
- **Анализатор даёт не все факты, нужные норме** — например, для
  [DDD-008](../../../rules/ddd.md#агрегат-ddd-006009) нужны типы полей сущности, и есть ли они
  в модели фактов, предстоит проверить → Недостающее попадает в границу среза, а не
  замалчивается: правило без фактов остаётся непроверенным, а причина видна в вердикте.
- **Проект на языке вне 18 поддержанных** → Подготовка состоится, срез будет пустым, а файлы
  попадут в перечень непросмотренных. Правила кода дадут `err`, а не `ok` — молчаливого
  зелёного прогона не будет.

## Migration Plan

1. Образ Trommel пересобирается: `make trommel-image` и `make trommel-image-verify` — с новой
   базой выполнения и анализатором внутри.
2. `trommel.yaml` дополняется составом среза. Контракты `docs` и `full` в части состава правил
   не меняются, записи `notes` для `CLAR`, `CQRS`, `DDD` остаются прежними.
3. `COVERAGE.md` перегенерируется целью `make trommel-coverage`. Ожидаемое расхождение —
   только идентификация условий прогона; состояния правил прежние.
4. Откат: возврат прежнего `Dockerfile` и снятие раздела среза из `trommel.yaml`. Прогон
   `docs`-контракта работает и без анализатора — правил, требующих фактов о коде, в его
   составе нет.

## Open Questions

  Вопрос решается изменением, реализующим эти правила; на состав уровней среза он не влияет.
